# MANTIS Accounting Root-Cause Matrix

Phase 1. Evidence is the current workspace source, commit `8070b217`, and the uncommitted diff on the posting policy. Production data was not opened. Scenarios are anonymised reconstructions of the reported failures, traced through this code.

Historical rows are not repaired by this audit.

## Classification of prior fixes

| Fix | Class |
| --- | --- |
| Central `postPaymentAccounting` plus posting policy (`8070b217`, extended in the workspace) | Root-cause improvement for "no single writer". Partial, because levy, expense, trust, manual journals, change stream, and the maintenance backfill still write beside it. |
| Workspace deposit-only predicate `amount <= 0` | Root cause fixed in source for new combined receipts. Not in `8070b217`. Historical rows untouched. |
| Committed predicate `amount <= deposit` | The defect. Still the committed behaviour. |
| Mismatch throw in `recordIncomeFromPayment` (`e17c3061`) | Root cause fixed for owner-income rental/sale disagreement, except `introduction`. |
| Webhook classification from `rentalType` only | Root cause fixed for that entry point. |
| 409 when multiple active accounts exist (`e17c3061`) | Valid safety stop. Symptom of duplicates remains, and it creates missing owner income. |
| Partial unique index and `archiveDuplicateActiveLedgers` | Partial. Index is opt-in. Archive does not merge transactions. |
| Manual merge endpoint (`099da38b`) | Valid tool. Not a prevention. Wrong keeper choice can hide history. |
| `accountingComplete` separate from `Payment.status` | Valid detection. Does not make the receipt look incomplete to a user who only sees status. |
| Idempotency key `payment:{id}` | Valid against double income on the same account. Does not correct a wrong account. |
| Scheduled startup ledger maintenance disabled | Valid. Prevents boot from rewriting history. |
| `sync_property_accounts` maintenance job still calling `recordIncomeFromPayment` and `migrateSalesLedgerForCompany` | Competing write path. Still reachable from the accountant sync endpoint. |
| Trust policy `skipTrust` for non-sale | Ineffective. The flag is not read by `emitPaymentConfirmedIfNeeded` or `postBuyerPaymentToTrust`. |

## What was ruled out

| Hypothesis | Result |
| --- | --- |
| Frontend `ledgerId` selects the book | No `ledgerId` on payment create. Server resolves the owner ledger. |
| Cash vs bank uses a different owner-income writer | `paymentMethod` is stored. Owner income and the receipt journal do not branch on it. |
| Paynow subscription billing is the rental path | It writes `BillingPayment`, not `PropertyAccount` income. |
| Ecosystem quote or notification posts rent | Ecosystem verify does not create a `Payment`. Notifications insert `Notification` documents. |
| Lease id selects the ledger | `leaseId` is workflow context. `resolveLedgerTypeForProperty` does not read it. |
| `property.type` (house, commercial) selects the ledger | It influences default commission percent only. |
| A single bug explains every missing owner-income case | Ruled out. The matrix lists independent causes that all produce the same symptom. |

## Database uniqueness — do not add the index yet

Existing duplicates make a blind unique index unsafe:

- `ensureLedgerIndexes` already catches duplicate-key failures and then archives extra active documents without merging their transactions.
- That archive makes owner income disappear from reports (`isArchived` excluded).
- The one-time cleanup key `property_account_duplicate_cleanup_v1` will not run again after it is marked complete, even if the index was never created.
- Documents with `isActive: false` and `isArchived: false` still occupy the unique key, while `getOrCreate` will not select them, so the next create hits a duplicate key and may fail the reload.

Phase 2 must inventory duplicate groups and define a non-destructive keeper rule before `ALLOW_ACCOUNTING_INDEX_MIGRATION` is turned on.
